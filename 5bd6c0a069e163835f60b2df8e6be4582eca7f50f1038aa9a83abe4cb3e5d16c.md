## Triage Result

**Decision:** TRUE POSITIVE
**Category:** N/A
**Confidence:** High
**Vulnerability Class:** XSS

**Summary:** User-controlled username data is inserted verbatim into the Pug template source before compilation and rendered as unescaped HTML in the user profile page, enabling stored XSS.

### Code

`routes/userProfile.ts:73-98`

```typescript
if (username) {
  template = template.replace(/_username_/g, username)
}
// ... (other placeholder replacements) ...
try {
  const fn = pug.compile(template)
  const CSP = `img-src 'self' ${user?.profileImage}; script-src 'self' 'unsafe-eval'`
  // ...
  res.send(fn(user))
```

The username from the database is spliced directly into the Pug template source string before `pug.compile()` is called, so any HTML or script content in the username becomes part of the compiled template and is sent to the browser as literal HTML.

### Review Scope

**Files examined:** `routes/userProfile.ts`, `views/userProfile.pug`, `lib/insecurity.ts`, `lib/utils.ts`
**Searched for:** `_username_` placeholder in Pug template, `isChallengeEnabled`, `authenticatedUsers.get`, `sanitize` usage in `userProfile.ts`

### Stage 1 — Vulnerability Verification

**Vulnerability in Code:** TRUE

The `_username_` placeholder in `views/userProfile.pug:44` (`p(style='...') _username_`) is replaced at `routes/userProfile.ts:74` via `template.replace(/_username_/g, username)` before `pug.compile(template)` is called at line 87. Inserting content into the Pug template source (rather than passing it as a template local) bypasses Pug's contextual output escaping entirely. The backslash prepended at lines 67–68 (`username = '\\' + username`) adds only a literal `\` character; browsers do not treat `\` as an HTML escape sequence and will still parse an embedded `<script>` tag. The challenge check at line 91 (`utils.contains(username, '<script>alert(\`xss\`)</script>')`) confirms the application itself expects a script tag in the username to trigger execution.

### Stage 2 — Impact Assessment

**Impact:** TRUE

XSS on a user profile page executing in the victim's browser session can be used for session-token theft, arbitrary action execution on behalf of the user, and phishing. Under the production code assumption, this is a full-impact stored XSS: a user sets a malicious username once (via the profile POST endpoint), and the payload fires on every subsequent profile page load without further attacker interaction.

### Stage 3 — Reachability Assessment

**Exploitable:** TRUE

- **External Input:** TRUE — the cookie `token` field (`req.cookies.token`, line 35) is attacker-supplied HTTP input; the username payload reaches the database via the profile-update route using user-supplied form input.
- **Trust Level:** Untrusted — cookies are client-side values; username is set by the authenticated user through the profile form and stored without sanitization before retrieval here.
- **Taint Flow:** Viable — `req.cookies.token` → `security.authenticatedUsers.get()` (line 35) → `UserModel.findByPk(loggedInUser.data.id)` (line 42) → `user.username` (line 53) → `template.replace(/_username_/g, username)` (line 74) → `pug.compile(template)` (line 87) → `res.send(fn(user))` (line 98). No sanitization, escaping, or validation touches the username between retrieval and template injection.
- **Sink Usage:** Dangerous — `res.send()` at line 98 delivers the compiled HTML to the browser; the username content embedded at the Pug source level is rendered as raw HTML, not as encoded text.

### Compensating Controls Found

- CSP header (`Content-Security-Policy: img-src 'self' ...; script-src 'self' 'unsafe-eval'`) is set at `routes/userProfile.ts:94–96`. This blocks `<script>` inline execution in browsers that enforce CSP, but it only reduces risk rather than eliminating it for two reasons: (1) the `profileImage` field is directly interpolated into the CSP header string at line 88 (`\`img-src 'self' ${user?.profileImage}; ...\``), allowing an attacker who controls their `profileImage` URL to inject additional CSP directives such as `script-src 'unsafe-inline'`; (2) the `'unsafe-eval'` directive remains, enabling eval-based script execution paths.

### Key Facts

- `views/userProfile.pug:44` places `_username_` as inline text inside a `p` tag; Pug does not HTML-encode plain inline text at the source level when it is a string literal in the template source.
- `routes/userProfile.ts:74`: `template.replace(/_username_/g, username)` injects username into the Pug source string prior to compilation, bypassing Pug's `=` (escaped output) mechanism entirely.
- `routes/userProfile.ts:67–68`: the backslash prepend (`'\\' + username`) is not HTML encoding; a `\` prefix before `<script>` does not prevent browsers from parsing the script element.
- `routes/userProfile.ts:55–66`: the SSTI branch using `eval(code)` is gated on `utils.isChallengeEnabled(challenges.usernameXssChallenge)`, but the XSS via direct template string injection (line 74) is not gated and is always active.
- `routes/userProfile.ts:88`: `const CSP = \`img-src 'self' ${user?.profileImage}; script-src 'self' 'unsafe-eval'\`` — `profileImage` is user-controlled and directly interpolated, enabling CSP header injection to add `'unsafe-inline'`.
- `routes/userProfile.ts:91`: the challenge solve condition explicitly checks `utils.contains(username, '<script>alert(\`xss\`)</script>')`, confirming script-tag payloads in the username do reach and execute in the rendered page.
- No call to any sanitization utility (e.g., `security.sanitizeHtml`, `security.sanitizeSecure`, or `entities.encode`) wraps `username` between database retrieval (line 53) and template insertion (line 74).
